# EDR — The `· edr:` mark is carried by the task that implements the governing code — sdd-tasks never schedules materialization as its own task

- **Status:** Accepted
- **Date:** 2026-08-31

## Contexto
This change's own verify run (`sdd/bound-apply-batch-length/verify-report`) flagged three CRITICALs in the `decision-gaps` backing check — tasks 5.1, 5.2 and 8.1 (see `contracts/two-totals-in-one-table-footer`, `contracts/est-lines-is-a-bare-integer`, `structure/serial-apply-dispatch-budget`). All three shared one cause: `sdd-tasks` grouped the three EDR materializations into their own dedicated Phases (5 and 8), separate from the Phases (1, 2, 3, 7) whose tasks actually implemented the governing code. Each materialization task's only `Files Changed` row was a path under `.matecito-ai/edr/` — exactly the shape the backing check flags, because there is no other path in that task's own changed-file set to prove the decision has implementation behind it. `~/.claude/references/decision-capture/in-flow-capture.md` already requires materialization to happen "in the **same work-unit step** that implements the code the decision governs — never a separate pass before or after" (`sdd-apply` Step 4b), but nothing at task-shaping time stopped `sdd-tasks` from writing a checklist that violated it before `sdd-apply` ever ran.

## Decisión
A task carrying `· edr: <domain>/<slug>` IS the task that implements the code the decision governs — never a standalone "materialize the record" task. `sdd-tasks` MUST NOT schedule a dedicated task or Phase whose sole purpose is creating or updating a `.matecito-ai/edr/<domain>/<slug>.md` file; materialization is not something the checklist schedules at all — it happens automatically, inside `sdd-apply`'s Step 4b, as part of the same step that implements the marked task. This rule is stated in `sdd-tasks`'s SKILL, in the same place its `· edr:` per-task contract already lives, citing `in-flow-capture.md`'s "same work-unit step" requirement rather than restating it in different words.

## Reglas verificables
- **[manual]** `sdd-tasks`'s SKILL states, next to the `· edr:` mark's own rule, that the marked task is the implementing task and that materialization is never scheduled as a separate task or Phase — citing `in-flow-capture.md`, not restating its wording.
- **[manual]** A tasks artifact MUST NOT contain a task or Phase whose entire purpose is producing an EDR file with no accompanying implementation task in the same unit — the `· edr:` mark travels on the code-implementing task itself.
- **[manual]** This rule governs future `sdd-tasks` runs only; it does not retroactively rewrite an already-shipped tasks artifact or apply-progress, and it does not by itself fix a violation already committed.

## Alternativas consideradas
(a) Leave it as an implicit convention, trusting `sdd-apply`'s Step 4b wording alone to keep code and materialization together — rejected: that is exactly the gap that produced this change's own three CRITICALs, because `sdd-apply` materializes whatever task the checklist marks, and by the time it runs the split is already baked in. (b) Add a script check to `validate-return.js` or a new tasks-artifact linter that flags a task whose only content is an EDR path — rejected for now: at `sdd-tasks` time no code has been written yet, so there is nothing on disk to check the task's Files Changed against; the check `sdd-verify`'s `decision-gaps` group already runs is the enforcement point, after the fact, not before. (c) Push the fix into `sdd-apply` instead, refusing to materialize from a task with no other governing content — rejected: the cause is upstream, at task-shaping time; fixing it in `sdd-apply` would let `sdd-tasks` keep producing the same broken split and only catch it one phase later, same place `sdd-verify` already catches it today.

## Consecuencias
Going forward, a tasks artifact interleaves each decision's materialization into the Phase that implements its governing code, instead of grouping every EDR into its own dedicated Phase — the checklist may look less tidy by that axis, but it is what keeps `sdd-verify`'s `decision-gaps` backing check meaningful instead of structurally unable to pass. This change's own three CRITICALs (tasks 5.1, 5.2, 8.1) are explicitly NOT retrofitted by this record: they stay archived as-is, with their cause named in `apply-progress` and here — the user chose to fix the rule, not rewrite the history that exposed the gap. Nothing here is enforced mechanically; a future `sdd-tasks` run that violates it again is caught only at `sdd-verify`'s existing backing check, same as before this record.
