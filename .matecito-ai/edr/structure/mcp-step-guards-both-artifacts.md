# EDR — The qmd install step's Check guards both the binary and the registration, not the registration alone

- **Status:** Accepted
- **Date:** 2026-09-01

## Contexto
Every existing MCP step (context7, codegraph, drawio, debugger, skillsmp, figma, canva) registers a server the host re-fetches per launch via `npx -y <pkg>@latest`, so its only durable artifact is the registration and `Check: !mcp.Find(name)` covers it completely. qmd distributes as a globally installed npm package instead, so it has two durable artifacts: the binary and the registration. codegraph has the same two-artifact shape and solves it with a separate guardian, `codegraphBinaryStep` (install.go:463), contributed through the manifest's `binaries` array. qmd was ratified out of that array: `sync.Detect` resolves binaries through hand-written per-binary blocks (sync.go:228-280), and adding qmd there would need a fourth block plus a `fetchLatestQmd`, which is out of scope here.

## Decisión
qmdMCPStep's Check reports pending when any of four holds, evaluated in this order: (1) the registration is absent (`mcp.Find`); (2) `resolveUserNpmBinDir()` fails (e.g. npm absent) — the honest answer, since the step cannot establish where its own qmd would live; (3) the qmd that wins on the running session's PATH resolves outside the directory this step installs into — provenance, an unresolved-path comparison against `resolveUserNpmBinDir()`, deliberately not following symlinks, and skipped entirely when the ambient lookup itself fails, since a failed lookup only means this session's PATH cannot reach a qmd, not that none is installed; (4) the executable this step installs is not in the directory this step installs into, or does not run there — presence and health, probed directly at that canonical absolute path (`resolveUserNpmBinDir()` + `check.RunVersion`), never through the running session's PATH, so a location that session's PATH has not picked up yet still counts as installed. Not finding the program on the session's search path no longer means "not installed" by itself (the former clause 2, `exec.LookPath("qmd")` failing) — that is now decided by looking at the directory this step actually installs into (clause 4). Provenance (3) runs ahead of presence/health (4), so a foreign qmd shadowing the install is still caught before presence/health would otherwise wave it through. Run reinstalls the binary unconditionally and registers with the host only when the registration is still absent, so a repair run does not attempt a duplicate `claude mcp add`; Run's own handling of a foreign qmd still shadowing the install after that point is a separate decision (`qmd-run-fails-on-shadowing-executable.md`).

## Reglas verificables
- **[auto]** qmdMCPStep's Check returns true when the registration is present but `resolveUserNpmBinDir()` fails (npm absent from the session's PATH) — `TestQmdMCPStep_Check_RegistrationPresentBinaryAbsent` (`internal/setup/install/install_qmd_test.go`).
- **[auto]** qmdMCPStep's Check returns true when the winning qmd runs fine but lives outside the canonical npm bin dir — `TestQmdMCPStep_Check_ForeignLocation` (`internal/setup/install/install_qmd_test.go`).
- **[auto]** qmdMCPStep's Check returns true when the qmd in the canonical bin dir is present but fails to run — `TestQmdMCPStep_Check_CanonicalButBroken` (`internal/setup/install/install_qmd_test.go`).
- **[auto]** qmdMCPStep's Check returns true when the registration and resolver both work but no qmd was ever installed into the canonical bin dir — `TestQmdMCPStep_Check_CanonicalAbsentWithResolverAvailable` (`internal/setup/install/install_qmd_test.go`).
- **[auto]** qmdMCPStep's Check returns false when a healthy qmd sits in the canonical bin dir even though that dir is absent from the running session's PATH — what a prior run installed and persisted does not depend on the current session having already picked it up — `TestQmdMCPStep_Check_CanonicalPresentButDirNotOnPATH` (`internal/setup/install/install_qmd_test.go`).
- **[auto]** qmdMCPStep's Check returns false only when the registration is present AND the winning qmd resolves inside the canonical npm bin dir AND it runs — `TestQmdMCPStep_Check_BothPresent` (`internal/setup/install/install_qmd_test.go`).
- **[auto]** a repair run (binary missing, registration present) reinstalls the binary and does not call `claude mcp add` again — `TestQmdMCPStep_Run_AlreadyRegistered_SkipsClaudeMCPAdd` (`internal/setup/install/install_qmd_test.go`).
- **[auto]** on a machine where the canonical qmd is the only qmd on PATH, Check reports not-pending and stays not-pending on a second call — `TestQmdMCPStep_Check_SecondRunIdempotent` (`internal/setup/install/install_qmd_test.go`).
- **[auto]** right after a successful Run, Check reports not-pending for what this step just installed — `TestQmdMCPStep_Check_NotPendingRightAfterRun` (`internal/setup/install/install_qmd_test.go`).

## Alternativas consideradas
(a) Registration only — `!mcp.Find("qmd")`, matching all six existing MCP steps verbatim. Discarded: leaves a machine that loses the binary out of band reporting nothing pending, forever — the host would launch a command that is not there, and no install or update run would ever repair it. (b) Declaring qmd in the manifest's `binaries` array so `codegraphBinaryStep`'s pattern gives the binary its own guardian — the structurally cleanest answer, and exactly how codegraph solves it, but weighed and rejected for this revision too: it buys `check.RunVersion`, which the step can already call directly, and gives no provenance clause at all — a foreign working qmd would pass `RunVersion` exactly as it passed the original `LookPath`-only Check. Its costs are real and concrete: a fourth hand-written block in `sync.Detect` (`sync.go`) plus a case in `Sync`'s switch, a new `fetchLatestQmd` doing a network call inside `Detect`, qmd appearing as a versioned component of `matecito-ai update`, and splitting qmd's guard across two mechanisms — falsifying this record's own stated Consecuencias below. (c) Reading `mcp.Find`'s connectivity as the pending gate — discarded: catches a broken binary but not a foreign-but-working one, and creates an unrepairable pending loop on a machine whose registration itself does not match how this step registers (e.g. `qmd mcp --watch` vs. `qmd mcp`), since Run never rewrites an existing registration. (d) Version comparison against the latest GitHub release — discarded: puts a network call inside the plan phase (an offline machine reports pending forever or silently degrades), and conflates "stale" with "not mine" when Run already installs latest unconditionally regardless of what Check finds.

## Consecuencias
The step's own Check is now the qmd binary's only guardian, and it guards two more things than it used to: where the winning binary resolves, and whether it runs. If this step's registration in mcpRegistry is ever removed while qmd remains installed via npm, that guardian disappears with it — unlike codegraph, qmd has no separate binaries-array watchdog. The canonical directory Check compares against is derived from the same read-only resolver Run itself uses (`resolveUserNpmBinDir`, split out of `ensureUserNpmPrefix`), so the two cannot drift into disagreeing about what "canonical" means. Check now costs one additional local exec in the common case (`npm config get prefix`, via the resolver) plus, when the location matches, one more (`qmd --version`) — both local, no network, so an offline machine is unaffected.
