# EDR — El presupuesto de despacho serial de sdd-apply vive inline en Guards, calibrado a 600 líneas desde un solo ciclo medido

- **Status:** Accepted
- **Date:** 2026-08-31

## Contexto
`sdd-tasks`'s return now carries a per-Phase `Est. lines` estimate (`### Breakdown`, see `contracts/est-lines-is-a-bare-integer`). A serial `sdd-apply` dispatch pays a rising per-request price as its prompt grows across a long change: one measured cycle ran nine hand-cut batches, ~190k–470k tokens each, and a 487-request run whose per-quarter price doubled over the cycle. Nothing today cuts a serial dispatch by that cost signal — only by scope (the Phase breakdown itself) and by reviewer-facing size (`### Review Workload Guard`, 400 changed lines). A mechanism was needed that reads the new `Est. lines` column and slices the dispatch before it is sent, without adding a user turn.

## Decisión
The cut lives as a mandatory, silent entry in the development fragment's `## Guards` — `### Apply Dispatch Budget (MANDATORY)`, shaped like `Parallel-Mark Validation`: mechanical, states its outcomes, degrades silently, never opens a gate. It walks `### Breakdown`'s `Est. lines` values in implementation order and cuts the serial dispatch into slices, at Phase boundaries only, whenever the running total would exceed **600** estimated lines. No new deployed reference file is created — five steps of prose do not justify another path a runtime instruction has to name correctly.

## Reglas verificables
- **[manual]** The guard entry lives inline in `payload/domains/development/CLAUDE.md`'s `## Guards`, between `### Review Workload Guard` and `### Validator Findings` — never as a new deployed reference file.
- **[manual]** The threshold is 600 estimated lines, accumulated over Phases in the order `### Breakdown` lists them (implementation order); the cut lands only at a Phase boundary — a single Phase is never split, even when its own estimate exceeds 600.
- **[manual]** The guard applies only to a serial `sdd-apply` dispatch: never inside a concurrent round, never across rounds, and never to a consolidation run — all three are named exclusions in the guard's own text.
- **[manual]** The guard runs unattended: it never opens a gate, never asks a question, and reports at most one notice line naming the slice count and each slice's Phase range; a slice count of one is not reported.
- **[manual]** An absent or unparseable `Est. lines` value degrades to exactly one dispatch, with no error, warning or mention — the guard's silent-degradation path, not a failure.

## Alternativas consideradas
(a) Extend `### Review Workload Guard` to also cover dispatch cost — rejected: that guard is interactive `ask-on-risk` by default and stops to ask the user; this cut is orchestration mechanics with no product impact, so it must stay mandatory and silent, and folding a silent mechanism into an asking one would make the asking one ambiguous about when it fires. `### Review Workload Guard` owns reviewer cognitive load (400 changed lines, a human reading a diff); this guard owns per-request dispatch cost (600 estimated lines feeding token growth) — two different axes that happen to share a unit. (b) Set the threshold at 400, matching the review budget — rejected: identical values make the two guards indistinguishable in effect and cut nearly every Phase into its own dispatch, defeating the purpose of batching Phases that share context economically. (c) A new deployed reference file next to `parallel-batch.md` — rejected: consistent with that precedent, but every new deployed path is one more path a runtime instruction has to name correctly, and five numbered steps do not carry enough content to justify it; inline in `## Guards`, shaped like `Parallel-Mark Validation`, was preferred.

## Consecuencias
**Provenance.** 600 is calibrated from a single measured cycle — nine hand-cut batches, ~190k–470k tokens each, and a 487-request run whose per-quarter price doubled over the cycle — NOT from a measured lines-to-cost curve; no such curve exists anywhere in this payload. Recalibration means comparing the next `scripts/sdd-cost-breakdown.py` run's output against these same numbers, not re-deriving the threshold from first principles. **Both failure directions are accepted, not mitigated.** Too low: the guard over-slices, and each extra slice re-pays the ~47–50k-token entry-prompt floor a fresh `sdd-apply` dispatch costs before it does any work — a real, measurable cost. Too high: the guard never fires, and nothing reports a guard that did not fire — this is the harder direction to detect, because a silently-too-high threshold looks identical to a change that is genuinely small. Neither direction is instrumented; both are named here so a future recalibration knows what it is trading off. **The guard keys on an estimate nothing verifies** — `sdd-tasks` authors `Est. lines`, no script checks it before dispatch, and `sdd-verify` does not check line counts after; a systematically low estimate turns the guard off silently and no signal reports it, same known limit as the two `contracts/` records this change also materializes.
